# 引き継ぎ書: 花霞（hanagasumi）プロジェクト

> 作成: 2026-10-18。Claude（AI）とユーザーの長い会話セッションを、新しいAIや開発者が引き継げるように書き起こしたもの。
> **会話の生ログではありません**（生ログは、作成時のAIの環境になかった）。会話の記録は、このファイルとTIMELINE.md、FINDINGS.mdに要約してあります。
> **最優先で読む順番**: 1→2→7（落とし穴）→8（ユーザーの作業スタイル）→9（次の一手）。

## 1. プロジェクトの目的
- ユーザーは、**交配ゲーム**（PC専用。同時に出す花は少数。ゲーム内でのリアルタイム生成はしない＝**事前生成**）の花「**花霞**」を作っている。
- 当初の相談: Blender 4.5（bpy、ヘッドレス）で、写実的な花びら1枚（薄い半透明、淡い紫とアイボリー、放射状の筋、縮れて巻き込む縁）を、手作業のスカルプトなしに、**手続き的に生成**したい。現状の課題は、「扇子のように整いすぎる」「縁が上下に波打つだけで、折り返して重なる形が弱い」「布や成形した紙に見える」。原因の1つは、単一の高さ関数 z=f(r,θ) では、折り返しが原理的に作れないこと。
- 経緯で方針が変わった（→ 5. 設計の決定）。**現在の方針**: 花びらは、**Meshy AIで生成した高品質モデルを「型」として事前に持つ**。形の連続変形（幅・反り）と、**花全体の遺伝子**（枚数、配置、色、グラデーション、大きさ）を、交配で受け継ぐ。「親2つの中間の形」は、花びら1枚ではなく、**花全体のレベル**で作る（ユーザーの判断: 花びらの形そのものまでは、混ぜなくてよい）。
- 雌しべ・雄しべは、まだ作っていない（ユーザー: 「まぁ雄蕊雌蕊はないけど」と試作を了承）。

## 3. 前提・制約（ユーザーが明言したこと）
- PC専用。同時に並べる花は少数（基本、めちゃくちゃ並べる描写はない）。約30万〜50万面/花でも、重さは問題にならない見込み（**未検証**）。
- ゲーム内のリアルタイム生成は、しない。生成は事前でよい。
- Meshy生成物のゲーム利用は、ユーザーがメールで問い合わせて、**OKとの回答を得た**（ユーザーの報告。**回答の原文・対象プラン・範囲は、AIは見ていない**。保管をお願いしている）。
- 色の「255色」は、適当に言った数字。**OKLCHで持つ**ことで決定。
- **ゲームエンジンは Godot（4系）**（2026-10-18、ユーザーが決定）。理由: 無料・規約リスクが小さい、標準マテリアルに逆光の透け（Back Lighting）・透過がある、glTFが標準、GDScriptがPythonに近く交配ロジックを移しやすい。花のデータは glTF で渡す想定。

## 4. 見本（Meshy）について
- 見本は、最初に渡された「パーツ分けの写真（花びら6枚＋雄しべ・雌しべ）」から、1枚ずつ画像を生成（「image 2.5」と呼ばれていた画像モデル）して、Meshy（モデル: Meshy 7.1）で3D化したもの、とのこと（ユーザーの説明。「〜っぽい」と曖昧）。プロンプトは、同じだったと思う、とのこと。
- 6枚のGLBは、**`assets/` に含まれる**（約156MB。ユーザーの指示で、公開リポジトリに入れた。再配布がMeshyの回答に含まれるかは、未確認 → `NOTICE.md`）。ファイル名の一覧は`assets/README.md`。
- MeshyのAI生成技術は、**オープンソースではない**（調べた範囲。GitHub組織の公開リポジトリは`.github`のみ。MCPサーバーとエージェント用スキルパックは公開されているが、APIのラッパーで、生成技術ではない）。論文・モデルの公開の有無までは、確認していない。
- 型の対応（ファイル名→型ID）は、`spec/hanagasumi_gene_spec.json` の `petal_type_library.types` にある。**旧ログのp3〜p6は、t3〜t6のこと**（例: `p5_fan` = t5）。

## 5. 設計の決定と根拠
| 決定 | 理由・証拠 | 状態 |
|---|---|---|
| 花びらは事前モデル（型）＋連続変形。花全体で交配 | 手続き生成（Cloth、解析式）では、折り返して重なる形が作れず、薄い膜の見た目に届かない。ユーザーは花全体の中間で足りる | ユーザー承認 |
| 連続変形は、花びらの座標系での拡縮と、法線方向のずらし | 空間を連続的に写す変換なので、新しく交差しない（推論）。辺の長さ0.8〜1.2倍で、折れ目の鋭さ（法線変化の95%点）の比が0.95〜1.08、重なりの割合の変化は±1.5ポイント以内（測定） | 検証済み（±20%まで） |
| 色は OKLCH（L, C_rel, H）。C_rel は、sRGB内の最大鮮やかさに対する比 | RGBや色相の数字を平均すると濁る。C_relなら、どの値でも表示できる色になる | ユーザー承認 |
| 混ぜ方: L, C_rel は直線補間、H は短い弧、無彩色(C_rel<0.05)の親の色相は使わない | 同上 | 実装済み |
| グラデーション: 強さを連続値で混ぜる（親にないなら0）。強さ≥0.1で有効 | 『どちらかの親にあれば出る』だと、子の100%に出た | 検証済み |
| **半径と高さを独立した遺伝子にし、花全体を横と縦で別々に拡縮して合わせる** | 半径だけを遺伝子にしても、層×開き角の相互作用で、親の範囲外になる（突然変異なしでも42%）。半径だけ独立にすると、高さが範囲外になった（38%） | 検証済み |
| **開き角は遺伝子にしない。高さ/半径の比に合うように、探索で自動決定** | 開き角を遺伝子にすると、世代を重ねて半径・高さと食い違い、12世代目の64%で拡縮の比が0.85〜1.20の外（0.56〜2.23）。自動決定なら0.99〜1.01、範囲外0% | 検証済み |
| 層（1/2）の遺伝子は、枚数と独立に持つ。枚数8未満では、見た目だけ1層 | 旧案（枚数<8なら遺伝子を1に書き換える）は一方向にしか働かず、12世代で2層の割合が0.33→0.06に落ちた（バグ） | 検証済み |
| 連続値は『平均＋親どうしの差に比例したノイズ(K)＋突然変異』。Kと突然変異は遺伝子ごとに調整 | 平均だけだと、世代ごとにばらつきが減り、12世代で花がほぼ同じ見た目に収束した | 検証済み（50世代） |
| 型の突然変異（花びら1枚ごとに6%）、色相の突然変異σ=16度 | 突然変異なしだと、50世代で型の有効数が5.7→3.3、色相のSDが0.34倍に減った | 検証済み（50世代） |

## 6. 環境・実行方法
### 6.1 環境（AIのサンドボックスで動作確認したもの）
- Ubuntu 24、**1 CPU、約4GB RAM、1コマンド300秒の制限**、`/bin/sh`（ブレース展開なし、`time`コマンドなし）。ネットワークは許可ドメインのみ（pypi、github等。Blender公式配布サイトには、繋がらなかった）。
- 公式Blenderは入れられなかったので、**PyPIの `bpy==4.5.0`（Python 3.11用のモジュール版Blender）**を使った。Ubuntuの標準Python(3.12)には、ホイールがない。
  ```
  scripts/setup_env.sh      # uvでPython 3.11を入れ、/tmp/bpyenv を作る
  ```
- 描画は **Workbench**（ヘッドレスで動く。EGLの警告は無害）。Eevee/Cyclesは未使用（質感・半透明は未検証）。
- 長い処理は、`setsid nohup ... &` でバックグラウンドにして、ログを確認する。**1CPUなので、並列は、速くならない**。メモリは、40万〜60万頂点のメッシュの解析を2本同時に走らせると、プロセスが落ちた。
- 作業ディレクトリは `/tmp/meshy`（中間ファイル: `t1..t6.npz`、`dec_t1..t6.npz`）。スクリプトは、この固定パスと、`/tmp/bpyenv/bin/python` を前提にしている。変えるなら、`sed` で置換する。

### 6.2 再現の手順
```
bash scripts/setup_env.sh                 # 環境
# （assets/ に、6枚のGLBが入っている）
bash scripts/load_all_glb.sh              # GLB→npz（/tmp/meshy/t1..t6.npz）→ 型の下処理（dec_t*.npz）
/tmp/bpyenv/bin/python src/flower/hanagasumi_flower_proto.py -- /tmp/meshy/flower          # 6種類の花を描画
/tmp/bpyenv/bin/python src/flower/hanagasumi_breeding_test.py -- /tmp/meshy/breed          # 親F2×F3の交配、子6つ
/tmp/bpyenv/bin/python src/flower/hanagasumi_longrun_test.py -- /tmp/meshy/long            # 50世代の集団試験（約5分）
```
**動作確認の範囲（2026-10-18、リポジトリ内のコピーで）**: 全スクリプトのコンパイル、`hanagasumi_longrun_test.py` が前回と同じ数値を再現すること（3設定とも一致）、`breed()`の読み込み。**再実行していないもの**: 描画系（flower_proto、breeding_test、generations_testの描画部分）、`verify_cloth_growth.py`、`analysis/`の各スクリプト（パスの置換は、`run_all.sh`と`run_lr.sh`の`GLB_DIR`のみ）。動かないときは、まず、パス（`/tmp/meshy`、`/tmp/bpyenv`）を疑う。

Clothの実験: `src/cloth/verify_cloth_growth.py`（使い方は、ファイル先頭のコメントと`--help`）。見本の写真の測定: `src/analysis/measure_reference_photo.py`。

## 7. 落とし穴・訂正の記録（同じ失敗を避けるために）
1. **付け根（最も細い端）の自動検出は、信用してはいけない。** 主軸の端の断面の小ささで検出すると、付け根が斜めの角にある花びら（t4,t6）で誤った。旧ロジックはt4,t5,t6を取り違え、修正ロジックもt4,t6を誤った。**最終的に、ユーザーが画像を見て確認**した（t4,t6は、正面の右下の尖った端）。新しい型を足すときは、`src/analysis/render_axes.py`で、付け根の候補を画像にして、ユーザーに確認してもらう。付け根を取り違えると、幅/長さ・最大幅の位置・折れ目の本数が、全部ずれる。
2. **Blender 4.5のCloth: `shrink_max < shrink_min`は、エラーなしで補正される**（ユーザーが発見）。負（膨張）を入れたつもりが、ゼロになる。対策: 頂点グループの重みを反転し、`shrink_min`を負方向に動かす。最終フレームでアニメ値が入力どおりかを、`assert`で確認している。
3. **`rest_shape_key`（辺の自然長を別形状から取る設定）は、私の環境では効かなかった**（Dynamic Meshの有無、キーを作る順序、正方形の単純なテストでも同じ。原因は未特定）。他のAIの回答が勧めていた方法だが、実現していない。
4. **h=0.007（約1.7万頂点）＋自己衝突ONは、Clothが破綻した**（成長ゼロの列まで潰れた）。原因は、自己衝突の距離が辺長に対して大きすぎること、またはQuality Stepsの不足と推測しているが、**切り分けは完了していない**（自己衝突OFFの再実行は、結果を確認できていない）。
5. **曲率とメッシュ密度の相関（-0.92）は、見かけだった**（法線のノイズ÷辺長）。スケールを固定した粗さで測り直すと、約-0.5〜-0.6。
6. 折れ目の本数の指標（`ring_k`など）は、**あてにならない**場面がある（設定15本でピークが14に出たが、見える山は約7本）。湾曲が強い花びら（t2,t3）でも、投影の重なりで狂う。見た目の目安は、「設定値の約半分が見える」。
7. 『全員に同じ強さで出る』『親の範囲外が多い』は、突然変異のせいではなく、**ルールの設計**のせいだった。毎回、突然変異あり/なしの比較で切り分けた。
8. 半径だけを独立にすると、高さが悪化した（**問題が移っただけ**）。遺伝子の追加では、他の指標が悪化していないかを、必ず測る。
9. 世代を重ねる試験は、**必ず回すこと**。1世代の試験では見えなかった収束（色相、半径、型）と、層のバグが、12世代で現れた。
10. 「元写真との2D比較」で使った指標は、**短軸/長軸**（常に1以下）で、付け根の向きに依存しない。『幅/長さ』とは別物。混同して一度、誤って「一致」と報告した。
11. ツールの制約: 1コマンド300秒を超えると、止められる。`sleep`で待つときは、280秒以内にする。バックグラウンドのプロセスは、`setsid nohup`で起動しないと、コマンド終了時に消えることがあった。

## 8. ユーザーの作業スタイル（応答の仕方）
- **日本語**で応答する。簡潔でカジュアルな文面を好む（業務連絡の文面作成時）。技術的な内容は、根拠と数字を示して簡潔に。

- Meshyの利用規約など、法的・権利的なことは、AIが断定せず、ユーザーが確認する（AIは弁護士ではない）。

## 10. 用語
- **型（type）**: 花びらの事前モデル。t1〜t6の6種類。
- **C_rel**: OKLCHの鮮やかさを、その明るさ・色相でsRGBに収まる最大値に対する比（0〜1）にしたもの。
- **K（SPREAD_K）**: 子の値に足す、『親どうしの差に比例したノイズ』の係数。世代ごとのばらつきの減少を防ぐ。
- **SD比**: n世代目のSD ÷ 0世代目のSD。1に近いほど、ばらつきが保たれている。
- **自己衝突、Workbench、頂点カラー**: Blenderの用語。
